# SpaceHuggers — Change Spec (2026-06-11)

This document is the implementation spec for the changes approved in the
2026-06-11 design session. **It is a plan, not a patch.** The user implements
the code; this spec is the review contract.

Scope of this document: **bundled pass 1 — camera zoom, performance, HUD
redesign.** The remaining items (polished Game Over panel, Start Panel, level
timer + scoring, bonus box) are spec'd separately at the bottom of this file
and will be implemented after pass 1 is reviewed and merged.

The user requested: futuristic HUD, polished Game Over, Start Panel, level
timer with faster-finish bonus, bonus box (destructible, in every level, with
a pulsing beacon), zoom out, performance. User confirmed: bonus box is
destructible on bullet hit, start panel first-load only, timer formula
`max(0, 1000 - elapsed*5)`, zoom is `4*9 → 4*8`.

The codebase is SpaceHuggers by Frank Force (JS13K 2021) running on LittleJS
v0.74, packaged as a Capacitor Android app for Fire TV. The `www/` directory
is a build mirror of root + `engine/`; do not hand-edit it. The mirror list
is in `scripts/sync-www.sh`. After any root edit, run `npm run sync:source`.

## Pass 1 — Camera zoom, performance, HUD redesign

### Change 1.1 — Zoom out the camera by ~11%

**Goal:** Default camera scale drops from `4*9 = 36` px/world-unit to
`4*8 = 32` px/world-unit. Effect: the player sees ~11% more of the world on
screen, useful for TV viewing.

**Files:** `app.js` (root + `www/` mirror).

**Edit:** `app.js:13`. Replace the line

```
const defaultCameraScale = 4*9;
```

with

```
const defaultCameraScale = 4*8;
```

**What propagates automatically (no edit needed):**
- `appUpdate:268–272` derives `cameraSize`, `renderWindowSize`,
  `gameplayWindowSize`, `updateWindowSize` from `cameraScale`. All
  re-derive at runtime, so they follow the new constant.
- `engine/glPreRender` reads `cameraScale` to build the projection matrix
  each frame; no engine change required.
- HUD is drawn in screen space, so it does not move.

**Verify after edit:**
- `appUpdate:439–446` — the camera clamp uses
  `mainCanvas.width/2/cameraScale` to compute horizontal bounds. Linear in
  `cameraScale`, so it widens correctly. **Read those lines after the
  change** to confirm the clamp math still keeps the camera inside the
  level horizontally. If the level is narrower than the new view, the
  camera will sit centered; if wider, it tracks the player as before.
- Internal canvas is `1280×720` (`engine/engine.js:38`). At scale 32, the
  view is `1280/32 = 40` world-units wide, `720/32 = 22.5` tall. Levels
  are `vec2(min(level*99, 400), 200)` (`appLevel.js:698`) — well wider
  than the view, so horizontal clamp remains active. Vertical: level
  height of 200 vs. 22.5 view = plenty of room. No clamp regression
  expected.

**Rollback:** Single-line revert.

**Risk:** Low. Single constant. Visual only.

### Change 1.2 — Performance: reduce starfield count

**Goal:** Lower per-frame starfield draw cost on Fire TV. The current loop
runs `for (let i = 1e3; i--;) drawTileScreenSpace(...)` per frame at
`lowGraphicsSettings = 0` (Chromium path). On the Fire TV WebView this is
a significant cost.

**Files:** `appEffects.js` (root + `www/` mirror).

**Edit:** `appEffects.js:352` area. The current code (paraphrased) is:

```
if (lowGraphicsSettings)
{
  // cap at 400
}
else
{
  for (let i = 1e3; i--;)
    drawTileScreenSpace(...)
}
```

Replace the unconditional `1e3` (and the 400 cap if present) with a single
named constant and reduce. Suggested:

```
const starCount = 300;  // was 1000 (low-end 400)
for (let i = starCount; i--;)
  drawTileScreenSpace(...)
```

If the existing cap-at-400 branch for `lowGraphicsSettings` exists, fold
both paths into the single constant above and remove the branch. If the
branch has *other* differences (e.g. star size, brightness, twinkle
rate), keep the branch but use 300 in the high branch and 150 in the
low branch. **Read the surrounding code first** to see what the
`lowGraphicsSettings` branch actually does.

**Verify after edit:**
- Sky still looks populated on a 1280×720 internal canvas. 300 stars is
  roughly the same density as a real night sky photo. Visually check on
  the Fire TV.
- FPS: expect a small but visible bump in the chromium path. To
  measure, temporarily flip `let debug = 1;` at the top of
  `engine/engineDebug.js`, press `0` to show the watermark, and read the
  FPS.

**Rollback:** Restore the original constant or the original branch.

**Risk:** Low. Pure render-cost reduction. No gameplay change.

### Change 1.3 — Performance: reduce explosion particle counts

**Goal:** Lower the particle cost of explosions, which are the largest
single source of per-frame overdraw in the game. Two emitters to tune:
`makeFire` and `makeDebris` (both in `appEffects.js`).

**Files:** `appEffects.js` (root + `www/` mirror).

**Edit:** In `appEffects.js:185–204` (approximate — read the file to
find the exact lines), find the `makeFire` and `makeDebris` functions.

Current behavior (paraphrased):
- `makeFire(pos, r=2)` creates an emitter with `r*r*30` particles
  (so `r=2` = 120 particles, `r=1` = 30 particles).
- `makeDebris(pos, r=2)` is similar.

Reduce:
- Change `r=2` callers' effective particle count by halving the
  multiplier, or
- Change the default `r=2` to `r=1.5` in the function signature so
  all callers benefit without touching call sites.

**Recommended approach:** lower the multiplier inside the function, not
at call sites. Find the line that looks like
`new ParticleEmitter(..., r*r*30, ...)` and change `30` to `15`. Do
the same for `makeDebris`.

**Verify after edit:**
- Big explosions still feel impactful at half the particle count. If
  they look weak, raise the multiplier to `20` (still a 33% saving).
- Smaller explosions (`r=1`) become `15` particles — still visible.
- Test on Canvas2D path (force `let glEnable = 0;` in
  `engine/engineWebGL.js:18`) to see worst-case FPS.

**Rollback:** Restore the original multipliers.

**Risk:** Low. Visual only. Players will not notice the missing
particles unless they see both versions side-by-side.

### Change 1.5 — HUD redesign (futuristic style)

**Goal:** Replace the existing pill-based HUD with a more angular,
futuristic treatment. Keep the same five elements (score, level, lives,
enemies remaining, kills), but change the visual language: thin
neon-style outlines, mono-style font, corner brackets instead of full
rounded pills, subtle additive glow.

**Files:** `app.js` (root + `www/` mirror). All HUD lives in
`appRenderPost` between lines 493–831.

**Visual spec:**

For each of the five HUD elements, render:

1. **A thin (1.5px) cyan/amber outline** — a rectangle 2px inset from
   the pill's outer edge, with the four corner segments *missing* (so
   the user sees an angular bracket at each corner, not a closed
   box).
2. **A dim translucent fill** at 15% alpha to keep the area readable
   against bright backgrounds.
3. **A label** in small (16px) all-caps mono style above or beside
   the value.
4. **A value** in medium (24px) bold style.
5. **A thin horizontal accent stripe** under the value, 30% the width
   of the pill, in the same accent color.

**Color palette:**
- Score: amber `#ffb347`
- Level: cyan `#7fdbff`
- Lives: red `#ff5050`
- Enemies remaining: green `#7fff7f` (changes to amber when 0)
- Kills: white `#ffffff`
- Accent brackets: cyan `#7fdbff`
- Background fill: black at 15% alpha

**Helper to add near the existing `hudPill`/`hudText` (lines 145–163):**

Add a new helper (do not replace the existing ones — keep them for
backward compat with the level-clear and pause panels that use them):

```

function hudFrame(x, y, w, h, color, alpha=0.15)
{
  // ... draw 4 corner brackets (L-shapes) and a translucent fill
}
```

**Existing code to restyle:**

| Current element        | File:line (approx) | New label   |
|------------------------|--------------------|-------------|
| Score pill (top-left)  | `app.js:540`       | `SCORE`     |
| Level pill (top-center)| `app.js:549`       | `LEVEL`     |
| Lives pill (top-right) | `app.js:554`       | `LIVES`     |
| Enemies pill (bot-mid) | `app.js:560`       | `THREATS`   |
| Kills pill (bot-left)  | `app.js:572`       | `KILLS`     |

For each one, replace the call to `hudPill` + `hudText` with:
- a `hudFrame(...)` call for the frame
- a small label call (16px, all caps, dim white)
- a value call (24px, accent color)

**Drop the emoji icons** (`⭐`, `♥`, `👾`, `☠`) — they look out of

**Keep the bottom-left control hint** (Fire TV / gamepad / keyboard

**Verify after edit:**
- All five elements are visible at 1280×720 internal resolution.
- No element clips outside the canvas edges.

**Risk:** Medium. The HUD is the most-played surface. Test all five

## Pass 5 — Bonus box (destructible, in every level)

Implemented `BonusBox` in `appObjects.js`. It is a destructible level
objective that responds to **player** bullet hits only. On bullet
impact it plays `sound_bonusbox`, destroys itself, and triggers the
normal level-clear state via `levelEndTimer.set()` (guarded so it does
not retrigger if the level is already ending). The game then proceeds
through the existing level-clear / time-bonus flow instead of calling
`nextLevel()` immediately.

**Spawn:** In `nextLevel()` after `applyArtToLevel()`, exactly one
`BonusBox` is spawned at a position found via `tileCollisionRaycast`
from the sky (same general placement pattern used for other grounded
placements). It receives a per-level color from `randColor()`.

**Visual (actual behavior):** Pulsing beacon with bobbing, additive
rect glow, and a non-rotating box sprite. The original plan mentioned
sprite rotation, but the implemented behavior intentionally removes the
box rotation while preserving the pulsing beacon and bob (`vec2(0,
sin(time*4)*.3)`).

**Hit detection (actual fix):** `BonusBox` still uses `setCollision(0,
0)` because it should not participate in solid-body physics. The box is
hit through `Bullet.update` overlap checks and `BonusBox.collideWithObject`.
In practice, the reliable fix was to give `Bullet` a small nonzero
collision size (`vec2(.25)`) so overlap queries consistently register
hits against the box. Enemy fire still does not trigger the box because
`BonusBox.collideWithObject` only accepts bullets whose attacker team is
`team_player`.

**Sound:** `sound_bonusbox` lives in `appEffects.js` with the other
`sound_*` constants.

**Risk / verification:** Medium. The critical regression points are:
- the box can be destroyed by player bullets
- enemy bullets do not trigger it
- destroying the box ends the level through the standard level-clear UI
- the box sprite no longer rotates, while the beacon still pulses/bobs

### Change 6.5 — Level generation: empty-map safety net

**Goal:** `app.js` was reporting "Threats - Area Clear" on freshly
generated levels. Two bugs conspired to produce a level with zero
enemies (and a HUD that read like the area was already clear).

#### 6.5a — Base-building loop returned 1 on the first `buildBase()` failure

`generateLevel()` (`appLevel.js:727-734` original) ran:

```js
for(let tries=99;levelEnemyCount>0;)
{
    if (!tries--)
        return 1;
    if (buildBase())
        return 1;  // ← the bug
}
```

`buildBase()` can legitimately fail when its own inner position-finder
times out (99 random X positions all within 30 of the player). The old
loop **aborted the entire level** on the first such failure, leaving
terrain with no bases and no enemies.

**Fix** (`appLevel.js:726-740`): `continue` instead of `return 1` on
`buildBase()` failure. The `tries` counter still bounds the total work
— only 99 consecutive failures abort the loop. With this in place, the
base loop will almost always succeed on the second or third attempt.

#### 6.5b — `propCount` could be 0 on every base

Even when `buildBase()` ran, the enemy-spawning block was gated on
`propCount = randSeeded(floorWidth/2)|0`, which rolls `[0, 4]`. If
every base happened to roll 0, no enemies were ever spawned — the
`levelEnemyCount` never decremented, the loop spun to 99 tries, and the
level retried 4× before giving up.

**Fix** (`appLevel.js:660-666`): the top floor now always spawns at
least 1 enemy regardless of the `propCount` roll:

```js
const enemyCount = topFloor ? max(1, propCount) : propCount;
for(let i = enemyCount; i--;)
{
    new Enemy(floorBottomCenterPos.add(
        vec2(randSeeded(floorWidth-1, -floorWidth+1), .7)));
}
```

#### 6.5c — Last-resort terrain spawn

`appLevel.js:762-782` adds a defense-in-depth check at the end of
`generateLevel()`. If `liveEnemies.size === 0` after the base loop and
the reachability pass — i.e. both 6.5a and 6.5b somehow failed to
produce an enemy — the function force-spawns up to 7 enemies directly
on the terrain via `tileCollisionRaycast`. The level will then always
have something for the player to hunt, even on a degenerate random
seed.

**Risk:** Low. The first two fixes are correctness-only; the third is
purely additive and only runs when both prior fixes didn't help.

**Rollback:** Revert each block individually if needed.

### Change 6.6 — Lives: 3 → 2 silent drop on initial spawn

**Goal:** The user saw only 2 hearts on the first frame of the game
even though `playerLives` is initialized to 3. The cause was the
`Player` constructor (`appCharacters.js:958`) doing
`--playerLives;` unconditionally — designed for respawns but
accidentally also firing on the very first spawn.

**Files:** `appLevel.js` (root + `www/` mirror).

**Edit:** `appLevel.js:1058`. Added `++playerLives;` immediately
before `new Player(checkpointPos);` in `finishLevelSetup()`. This
mirrors the existing `++playerLives` compensation that `app.js:851`
already does for the "player joins mid-game" path. After this change,
`playerLives` is 3 at game start, 2 after the first death, 1 after the
second, 0 → game over on the third — matching the spec.

**Risk:** Low. One-line compensation; no other path through the
`Player` constructor is affected.

**Rollback:** Delete the added `++playerLives;` line.

The original change record is kept here for reference:

**Goal:** The Fire TV fluidity log on 2026-06-14 showed the tile-bake
phase blocking the main thread for ~1.1 s per level transition (fg 675
ms, bg 440 ms on a 99 × 100 level). This caused cascading
`key event latency detected [Latency: 800-3000+]` warnings and a
progressive frame-drop spiral (dropped=453 → dropped=1519 → dropped=2604
over 30 s).

**Root cause:** `TileLayer.drawAllTileData()` (`engine/engineTileLayer.js:218-223`)
iterated every cell in the layer and called `drawTileData()` for each.
`drawTileData()` then went through `drawCanvas2D()`, which did a full
`context.save()` / `translate()` / `rotate()` / `scale()` / `restore()`
cycle per tile — 9 900 such cycles per layer, plus 9 900 redundant
`clearRect()` calls (the canvas was already cleared by `redrawStart()`
setting `canvas.width = w`).

**Fix** (`engine/engineTileLayer.js:224-287`): rewrote `drawAllTileData()`
as an inlined fast path. The new loop:
1. indexes `this.data` directly to skip the per-tile `vec2()` allocation
   in `getData()`
2. sets `imageSmoothingEnabled` once
3. uses `fillRect` for untextured tiles (`d.tile === 0`)
4. uses `drawImage` (no rotation, no mirror) for textured tiles
5. falls back to the slow `drawTile()` path only for the ~2-3 % of
   tiles that have a non-zero `direction` or `mirror` (mostly dirt
   tiles)

A `skipClear` parameter was also added to `drawTileData()` so the
incremental-update path (`setData(pos, data, true)`) still clears the
old tile before drawing the new one.

**Measured impact** (Fire TV, lowGfx, level 1, 99 × 100):
- Before: full bake ~1 100 ms (fg 675 + bg 440)
- After:  full bake ~150-250 ms (fg + bg)
- Direct reduction in level-transition main-thread block: ~80 %
- Indirect reduction: the shorter block prevents the key-event latency
  warnings from compounding into a runaway dropped-frame spiral

**Files:** `engine/engineTileLayer.js` (root + `www/` mirror).

**Rollback:** Restore the original `drawAllTileData()` body (one for
loop) and remove the `skipClear` parameter from `drawTileData()`.

**Risk:** Low. The Y-flip math matches `drawCanvas2D()` byte-for-byte
(verified: `h - (y + 1) * ts.y` for the rect's top edge). The slow-path
fallback covers the rotated/mirrored tile case identically to the

### Change 6.9 — Tile-bake multiply tint (color regression fix)

**Goal:** After change 6.8 the player reported "not everything is
grey(whiteish)" — the dirt/bases were showing the raw texture
colors instead of the per-tile tint. Root cause: the engine's
`drawTile()` (Canvas2D path) applies an RGB tint via
`globalCompositeOperation = 'multiply'` to reproduce the same
`color×texture` multiplication the WebGL shader does
(`engineDraw.js:68-74`). The original `drawTileData()` went through
`drawTile()` and inherited this tint. The new inlined fast path drew
the texture directly and **forgot to apply the multiply tint**.

**Fix** (`engine/engineTileLayer.js:268-285`): after the
`context.drawImage()` in the fast path, when the tile color is not
pure white (`color.r/g/b < .99`), apply the same multiply rect as
the engine does:

```js
if (d.color.r < .99 || d.color.g < .99 || d.color.b < .99)
{
    context.globalCompositeOperation = 'multiply';
    context.fillStyle = 'rgb(' + (d.color.r*255|0) + ',' +
                             (d.color.g*255|0) + ',' +
                             (d.color.b*255|0) + ')';
    context.fillRect(px, py, ts.x, ts.y);
    context.globalCompositeOperation = 'source-over';
}
```

The guard is what makes this cheap: the common case for pipes /
ladder / base is `new Color()` (white), which skips the composite-mode
switch entirely. Only the dirt (`levelColor.mutate(.03)`) and a few BG
tiles actually need the tint.

**Files:** `engine/engineTileLayer.js` (root + `www/` mirror).

**Rollback:** Delete the `if (d.color.r < .99 || ...)` block.

**Risk:** Low. The `multiply` blend is exactly what the slow path
produced; the cost is a single extra `fillRect` per tinted tile.

### Change 6.10 — Panel font-string cache (per-frame allocation cut)

**Goal:** When the PAUSE / GAME OVER / SCOREBOARD / NAME-ENTRY
panels are open, the user reported the WebView memory "blowing up".
`hudText()` and `hudMonoText()` previously built a fresh
``bold ${size}px impact`` / ``${bold?'700':'500'} ${size}px monospace``
template-literal string on **every** call. The scoreboard draws 50+
strings per frame, the name-entry keyboard 30+, the pause menu 10+.
That's 3000-6000 string allocations per second while a panel is open —
enough to cause sustained GC pressure and progressive heap growth
on Fire TV's limited-memory WebView.

`style|size`. The font string is built once per unique (style, size)
pair and reused thereafter. The cache is bounded — there are
roughly 10 distinct (style, size) combinations across the whole app
(16, 18, 20, 22, 24, 26, 28, 32, 36, 52 px), so the map never grows
beyond ~20 entries.

The scoreboard's rank label was also a per-row `padStart` allocation;
replaced with a constant `'0' + (i+1)` for i < 10.

**Files:** `app.js` (root + `www/` mirror).

**Rollback:** Replace the `_getHudFont(...)` calls with the original
`` `bold ${size}px impact` `` template literal.

**Risk:** Low. Same font string is produced; the cache just avoids
re-allocating it.

The original change record is kept here for reference:

### Change 6.11 — Canvas2D additive-color blend (WebGL parity)

**Goal:** With the WebGL path unavailable on Fire TV after a GPU
process crash (`glEnable=0`), the engine's `drawTile()` Canvas2D
branch only applied the per-tile `color` tint via `multiply` blend —
the `additiveColor` parameter (the `+ e` in the WebGL fragment shader
`gl_FragColor = texture2D(j,v)*d + e`) was **ignored**. This made
burning characters, hit sparks, weapon flashes, laser sight, and
every other additive-glow effect silently disappear in Canvas2D
mode — the "greyish" the user reported after the tile-bake
performance change.

**Fix** (`engine/engineDraw.js:78-99`): after the multiply pass, if
`additiveColor` has any non-zero RGB component, apply a second
`fillRect` under `globalCompositeOperation = 'lighter'`. This is the
Canvas2D equivalent of the shader's `+ e` (additive). The
`'source-over'` reset is critical — without it the WebView may stay
in `'lighter'` mode for the next `drawImage` call and over-bright the
texture.

```js
if (additiveColor.r || additiveColor.g || additiveColor.b)
{
    context.globalCompositeOperation = 'lighter';
    context.fillStyle = 'rgba(' + ... + ',' + additiveColor.a + ')';
    context.fillRect(-.5, -.5, 1, 1);
    context.globalCompositeOperation = 'source-over';
}
```

The WebGL path is unchanged — it still passes both `color.rgbaInt()`
and `additiveColor.rgbaInt()` to `glDraw`. So switching back to
WebGL mode (or rebuilding without the GPU crash) gives the same
output as before.

**Files:** `engine/engineDraw.js` (root + `www/` mirror).

**Rollback:** Delete the `if (additiveColor.r || ...)` block.

**Risk:** Low. The `'lighter'` blend is per-tile and scoped via the
existing `drawCanvas2D` `save/restore`. The composite-mode switch
is skipped when the additive is pure black (the common case —
`additiveColor = new Color(0,0,0,0)` for most objects), so there's
no per-frame cost for unaffected objects.
